# Aeris — архитектура

Проектное описание. Имена модулей ниже логические, а не утверждение о существующем коде.

## 1. Разделение процессов

```text
Aeris.exe (WinUI 3, непривилегированный GUI)     aeris (CLI из PATH)
                  |                                  |
                  +--------- Named Pipes ------------+
                                  |
                        AerisCore (служба Windows)
                                  |
                         aeris-core.exe (Rust)
           +----------+----------+----------+----------+
          Config    VPN/TUN     DNS       DPI       API/metrics
                       |         |         |
                   Routing / shared metadata / resources
                       |                   |
                     Wintun             WinDivert
```

Схема логическая: служба контролирует жизненный цикл и привилегированные операции; точное разделение IPC endpoint между службой и ядром проектируется с учётом ACL. Ядро поддерживает foreground/headless/служебный запуск, portable и непривилегированный режим с явным сообщением о недоступных привилегированных функциях. GUI и CLI могут работать одновременно. Единый экземпляр ядра на выбранном IPC endpoint; операции сериализуются. Сбой GUI не останавливает ядро; сбой модуля восстанавливает модуль, если процесс жив; фатальный сбой процесса затрагивает все его модули.

CLI `aeris` доступен в pwsh и скриптах независимо от рабочей директории. Установщик регистрирует PATH, standalone-поставка имеет регистрацию/удаление собственного PATH без повреждения чужих записей. Из-за конфликта `Aeris.exe` и `aeris.exe` в Windows выбрать и протестировать обёртку или отдельный каталог с однозначным поиском; не полагаться на различие регистра или профиль PowerShell. Проверять `Get-Command aeris` при установленном GUI и в portable. Абсолютные и относительные пути конфигов; JSON (`--json`), отключаемый цвет, коды завершения, help, автодополнение pwsh.

Команды (семантика согласована, точные аргументы будут задокументированы после проектирования CLI): `start`, `stop`, `restart`, `status`, `version`, `run -c <path>`, `vpn start|stop|restart`, `zapret start|stop|restart|strategies|select|test`, `dns restart|flush`, `config test|reload`, `proxy list|select|test`, `logs`, `diagnose`, `update`, `help`. `start` не должен неявно включать все модули. Отдельные команды службы/регистрации PATH нуждаются в спецификации. Управление запущенным процессом — через IPC, не запуск второго ядра.

## 2. Внутренние модули

| Модуль | Обязанности |
|---|---|
| Lifecycle | Состояния, старт/остановка, контроль отмены, health, watchdog |
| Config | Парсинг, типизация, валидация, immutable snapshots, reload/rollback |
| Transport | TCP/UDP, асинхронные сокеты, пулы, backpressure, таймауты |
| TLS | Проверенный TLS, сертификаты, профили отпечатков, REALITY и проверенные криптопримитивы |
| Protocols | Адаптеры исходящих протоколов и XHTTP/XUDP, общая реализация WireGuard и AmneziaWG |
| TUN | System, RIPS, Mixed, Auto; драйвер, маршруты, IPv4/IPv6 |
| DNS | Резолверы, политики, Fake-IP, кэш, hijack, защита утечек |
| Routing | Компиляция правил, группы, health checks, выбор исходящего маршрута |
| Sniffer | Метаданные HTTP Host/TLS SNI/QUIC в пределах возможностей без MITM |
| DPI | Нативная Rust-реализация семантики Zapret2, Lua runtime, стратегии и списки |
| Resources | Проверка, атомарное обновление и откат подписанных ресурсов |
| API/IPC | REST/WS совместимость, native IPC, события, capabilities |
| Observability | Метрики, журналы, диагностика, отчёты без секретов |

Cargo workspace; не создавать C-FFI движок Zapret или отдельные процессы winws/winws2. Внешние подписанные драйверы Wintun/WinDivert допустимы. mlua и rustls служат исходными кандидатами. Выбор Lua runtime сохраняет совместимость API и стратегий, изоляцию и лимиты. TLS сохраняет проверку сертификатов, профили отпечатков, REALITY и проверенные криптографические библиотеки. Источники отпечатков: uTLS, FlClashX, проверенные данные реальных браузеров и другие лицензируемые источники; ежедневная проверка, подпись, история, откат; REALITY и ML-KEM проверять на совместимость. Запрещены молчаливые несовместимые подстановки профиля.

WireGuard и клиентские варианты AmneziaWG используют общую реализацию в Aeris-Core. Официальные различия версий и их параметры обфускации учитываются внутри протокола. Сохраняются обычный WireGuard, общая маршрутизация, DNS, TUN, прокси-группы и цепочки. Официальные реализации других ОС служат эталоном поведения и межоперационных тестов. Целевой клиент остаётся Windows x64. Криптография и семантика протокола следуют официальным реализациям.

## 3. Сетевой путь

Вход TUN/локальный proxy → определение метаданных (DNS/Fake-IP/sniff/process) → первое совпадение пользовательского или провайдерского правила → группа/исходящий маршрут → DIRECT либо транспорт прокси. DPI по умолчанию на подходящих DIRECT-потоках, с исключением сокетов VPN-транспорта и служебного трафика, явная политика для ZAPRET/DIRECT-NO-ZAPRET. Трафик DNS использует свои утверждённые маршруты; избегать циклов DNS↔proxy bootstrap. Standalone DPI может работать без захвата VPN. Нужны тесты исключения повторного перехвата/зацикливания и согласования WFP/WinDivert/TUN.

System: системный стек. RIPS — собственный пользовательский сетевой стек Aeris на Rust. На этапе 9 сравнить реализацию с MIPS и подходящими альтернативами. Публичное имя режима сохраняется. Mixed: TCP System, UDP RIPS. Auto: обоснованный выбор с наблюдаемым состоянием и без ослабления безопасности. Архитектурные идеи gVisor можно изучать на этапе 9. Клон gVisor исключён. Сохранять IPv4/IPv6 и per-module исключения (IP/приложения/интерфейсы там, где поддержано). Выбор семейства IP и политики IPv4/IPv6 отдельно для сетевых модулей; Happy Eyeballs, NAT64/DNS64 при настроенной поддержке; BBR3/CUBIC — по реальным возможностям реализации и тестам, не подмена параметра названием.

Текущий транспорт использует Tokio. Ограниченные очереди и буферы, backpressure, отмена при остановке и таймауты обязательны для любого runtime. Сохранять CPU dispatch SSE/AVX2/AVX512, AES-NI/VAES/SHA/BMI по наличию и пользе. Не задавать произвольную affinity. Сравнительные бенчмарки определяют размеры кэшей, пулы и настройки. Снимки правил атомарны; активные соединения сохраняют выбранный маршрут по умолчанию до завершения, если политика безопасности не требует немедленного прекращения.

## 4. DNS

Резолверы UDP/TCP, DoH h1/h2/h3, DoT, DoQ; опциональный DNSSEC, TLS verification, optional pin, ECS opt-in, stamps при поддержке. Системный DNS — только явная настройка. Группы DNS select/parallel/sequential/fallback/load-balance/smart, отдельный маршрут для DNS, bootstrap и полное respect-rules, nameserver-policy, hosts, суффикс маршрута `#<группа>`. Без незаявленного публичного fallback. Возможна отдельная политика DNS для Zapret2. DNS Always On и DNS Proxy Access — независимая работа DNS и внутренних прокси-доступов при отключённом пользовательском VPN, с соблюдением ограничений и Kill Switch.

Fake-IP/Redir-Host/Hybrid: раздельный DNS-кэш и таблица Fake-IP IPv4/IPv6, стабильные соответствия, исключения, отсутствие fake-адресов во внешних запросах, интеграция маршрутизации/sniffer/DPI. TTL/negative cache/prefetch/serve-stale/coalescing, опциональное дисковое хранение раздельно; алгоритм вытеснения выбирается бенчмарками: сравнивать hit rate, p50/p95/p99 latency, throughput, расход RAM/CPU, поведение при смене сети и различных распределениях запросов. Это критерии инженерного выбора, не заранее заданные численные пороги. Пулы, TLS resumption, health, delayed racing, warmup/preconnect при пользе, реакция на смену сети.

Hijack UDP/TCP 53 IPv4/IPv6; standard (default), strict, custom, off; fail-closed для настроенной политики. Опционально блокировать известные внешние DoH/DoT endpoints без MITM; нельзя обещать обнаружение всех шифрованных DNS. Защита rebinding с явными исключениями. Раздельная очистка DNS/Fake-IP, атомарное обновление, диагностика утечек и задержек. Sniffer HTTP Host/TLS SNI/QUIC без расшифровки прикладных данных; ECH ограничивает видимость.

## 5. Маршрутизация и мониторинг

Первое совпадение; домен/IP/ASN/процесс/порты/протокол/интерфейс/логические выражения и утверждённые sub-rules. Использовать атомарно публикуемые неизменяемые снимки данных. Индексы, tries и кэши выбираются по измерениям с сохранением порядка. Rule/global/direct/zapret-only/custom в поддерживаемых сценариях; группы select/url-test/fallback/load-balance/smart/adaptive, weights/sticky/least latency/least connections. Smart выбирает подходящий узел, adaptive распределяет с учётом доступной пассивной статистики (RTT, jitter, TTFB, loss, скорость), без выдуманной нагрузки удалённого сервера. Профили gaming/streaming как политика, не обещание улучшения. Health при старте/по интервалу/lazy; общий dedup проверки узла+URL, ICMP отдельно от proxy request delay, несколько тестовых URL при поддержке. Непрерывный speedtest не выполнять. GeoIP/GeoSite/MRS/MMDB/YAML/text providers, кеш/обновление/история/rollback/источники. dialer-proxy для цепочек.

Kill Switch: off, proxy-only (default), strict, persistent согласно контракту; WFP и тесты на аварии. Не ослаблять правило автоматически при недоступном прокси. Точное значение режимов закрепить в YAML/API до кода. Соединения: live counters, правило/маршрут/DPI отдельно, закрытие отдельного/всех/по приложению при поддержке, настройки таймаутов, сохранение маршрута при обновлении. Диагностика симуляции правил, конфликтов и попаданий.

## 6. Zapret2

Aeris-Core реализует единую семантику Zapret2 нативно на Rust. Приоритет эталонов задан в [UPSTREAM.md](UPSTREAM.md). На этапе 10 проверяются зрелость перехода Flowseal и актуальные ревизии всех трёх источников. Завершённый Flowseal на Zapret2 определяет основную архитектурную и функциональную базу. Оригинальный Zapret2 определяет совместимость механизмов обработки пакетов, параметров движка и Lua API. Zapret2-gui дополняет их совместимыми стратегиями, функциями, автоматизацией и архитектурными решениями.

Изучить актуальные стратегии Flowseal, библиотеки Lua, параметры движка, списки и исключения, автоподбор, диагностику, управление WinDivert и жизненный цикл компонентов. Адаптировать применимые решения в Rust с проверкой лицензий, безопасности, производительности и стабильности. Поддержать проверенные стратегии Flowseal на Zapret2, их импорт и обновление. Унифицировать форматы, Lua API, списки, управление ресурсами и тесты. Сохранять оригинал стратегии и явно диагностировать неподдерживаемые возможности. Исключены движок, параметры, форматы, конвертация и любые слои совместимости, предназначенные только для Zapret1. Произвольные BAT/CMD и системные команды Lua запрещены.

Сохраняются rules-only/STRICT SPLIT, FULL BYPASS в пределах совместимых стратегий и standalone/custom. Клиент показывает ограничения Ultimate/custom и других стратегий. Lua требует проверенной изоляции по модели угроз, ограничений времени/памяти/файловой системы и валидации путей и аргументов. Подписанные драйверы проходят собственные проверки. Повторный перехват, циклическую маршрутизацию и конфликт VPN/DNS/DPI проверяют при интеграции.

Списки hostlist/IPSet/auto/exclude, пользовательские и провайдерские источники, provenance, дедуп, исключения приоритетнее включений, конфликтующие записи видимы. Обновление атомарно и с совместимостью движка. Автоподбор quick/standard/extended/custom, заданные цели, историю сохранять; применение результата вручную по умолчанию, не менять стратегию молча. Четыре основных HTTPS-проверки YouTube, GoogleVideo, Discord Gateway, Discord Voice API; отдельно можно проверять QUIC, но не считать HTTPS Voice доказательством доступности UDP-голоса. Все через нужный DIRECT-путь и DNS ядра. Ручное переключение сетевого профиля по умолчанию, наблюдение/автоопционально. Проверять драйвер, конфликты, античиты без вмешательства в них, CPU/ОЗУ, DNS, логи.

## 7. API и хранение

Совместимый Clash REST/WebSocket плюс собственный версионированный API; native Named Pipes с MessagePack, external JSON. Событийные изменения вместо постоянного polling, трафик/соединения ~1 с, CPU/DNS/DPI агрегаты ~2 с, статус немедленно; shared memory лишь при доказанной пользе. Нативный API и IPC начинают с v1, версионируются независимо и объявляют capabilities. Локальный API default, remote off, ACL/token, read/operator/admin/custom capabilities, привилегированные действия авторизованы отдельно. Не принимать произвольные команды. GUI не выполняет сетевое управление напрямую.

Настройки установленного клиента LocalAppData, portable рядом с программой, служебные общие данные в ProgramData при необходимости; ACL, DPAPI для токенов. YAML подписок read-only; настройки JSON/YAML, выбранное локальное хранилище для истории и статистики. SQLite остаётся кандидатом. Смена хранилища требует совместимой миграции и отката. Нет общей пользовательской резервной копии настроек. Внутренние атомарные snapshots для rollback допустимы.

Логи используют выбранный backend. tracing остаётся кандидатом. Уровни модулей off/error/warn/info/debug/trace, память/файл/hybrid; default warn, 8 МБ memory, disk off; DNS safety 4 МБ memory только ошибки/безопасность по умолчанию; журнал запросов не включать по умолчанию, отдельная настройка полей/анонимизации/исключений и ограничений, без раскрытия чувствительных данных, DPI basic 4 МБ, Lua warn/trace off. История соединений off, live/aggregates on; при включении 7 дней/100 МБ (настраиваемо); без payload. История автоподбора on. Неблокирующие буферы, счётчик отброшенных сообщений, redaction секретов, scrubbed export без автоматической отправки. Метрики отдельно от журналов.

## 8. Надёжность и обновления

Служба с watchdog и backoff, ограничение циклов перезапуска, safe mode, причину записывать в журнал. Атомарные настройки/ресурсы, migration rollback. Восстанавливать собственные сетевые объекты после сбоя без разрушения чужих. Kill Switch не обходить даже при рестарте. Совместимость IPC до обновления; подписанные manifest, hashes, доверенные ключи вне управляемого провайдером URL, откат. Отдельные обновления ядра, клиента, службы, Wintun, WinDivert, Lua-ресурсов, TLS, стратегий/списков и геоданных. Драйверы с подтверждением; без самопроизвольного удаления общих драйверов. Загружать только изменившиеся компоненты; явный возврат Nightly → Release при совместимости и безопасной миграции.

При недостатке RAM освобождать безопасно вытесняемые кэши с backpressure, не удаляя активные соответствия Fake-IP и данные, необходимые для текущей политики. При повреждении ресурса: обнаружить ошибку проверки целостности, не активировать повреждённый ресурс, восстановить последнюю проверенную совместимую копию или скачать и проверить новую; если безопасной копии нет, явно сообщить ошибку и не ослаблять политику. После смены сети/сбоя DNS восстанавливать configured resolver/policy и пулы с ограниченными повторами; никаких скрытых системных или публичных fallback. Проверять сохранение активных соединений там, где безопасно.

## 9. Предпосылки для подключаемых модулей

Сохранять слабую связанность и чёткие обязанности WinUI 3, ядра и системных служб. Использовать узкие, версионируемые внутренние контракты и IPC с возможностями, проверяемыми на стороне владельца операции. У GUI остаются будущие точки расширения WinUI 3. Ядро оставляет место для расширения через ограниченные границы вне критического пути. Привилегированные службы сохраняют независимость. Дополнительные компоненты смогут версионироваться и обновляться отдельно, а базовые клиент и ядро загружаются и работают без них. При проектировании предусмотреть будущую изоляцию, явное разграничение разрешений и изоляцию сбоев. Произвольный сторонний код запрещено загружать непосредственно в привилегированное ядро и системные службы.

Ввести только границы, которые нужны существующим компонентам. Не добавлять гипотетические интерфейсы, зависимости, платформенные прослойки или работу в критическом пути обработки пакетов ради отложенных модулей. Сохранять нативную интеграцию с Windows. Универсальная система позволит расширять продукт независимо от пересборки основных приложений. Публичные контракты, SDK и архитектуру исполнения определить после стабилизации внутренних компонентов на [отдельном этапе](ROADMAP.md#отложенный-этап-подключаемых-модулей).

## 10. CI/CD и переиспользование компонентов

Целевые сборки выполняются на бесплатных стандартных GitHub-hosted Windows x64 runners. Использовать предустановленные Visual Studio, MSVC и Windows SDK при подтверждённой совместимости. Другие стандартные hosted runners допустимы для проверок исходников и данных, которые не выпускают клиентские бинарники. Self-hosted, Larger Runners, платные образы и увеличение платных лимитов исключены. Репозитории клиента, ядра и ресурсов сохраняют свои границы.

Кэш инструментов и зависимостей отделён от кэша компиляции и готовых компонентов. Для Rust текущий выбор — sccache с отключённым Cargo incremental для обёрнутых вызовов. Не дублировать большой кэш компиляции кэшем `target` без доказанной необходимости. Выбор .NET SDK учитывает инструменты runner. Для NuGet и WinUI использовать фиксированный граф пакетов, изолированный путь и locked restore. Кэшировать совместимые сторонние библиотеки, упаковщики, Wintun/WinDivert, Lua, стратегии, списки и геоданные по мере появления точных версий, проверок и доказанной пользы. Инкрементальная компиляция C# или C/C++ требует проверки фактического генератора, совместимости и измерений.

Переиспользование применимо на реальных границах GUI, Core, службы, CLI, драйверов, ресурсов и дистрибутивов. Единое ядро сохраняет текущую архитектуру. CLI-обёртка использует проверенный бинарник Core. Ключ повторного использования готовых файлов точный и покрывает относящиеся к компоненту исходники, зависимости и lock-файлы, версии компилятора/SDK и образа, x64 target, профиль и параметры сборки, её рецепт, конфигурацию и версии контрактов. Изменение зависимости инвалидирует использующий компонент. Если проверенного результата нет, компонент пересобрать. Проверки остаются обязательными.

GitHub Actions Cache ограничен одним репозиторием. Передача в другой репозиторий требует явного набора артефактов успешных доверенных запусков: репозиторий, workflow, источник и точный SHA, run ID и попытка, immutable artifact ID, версия компонента и контрактов, параметры сборки, инвентарь файлов и SHA-256. Проверять происхождение и целостность артефакта, совместимость всех выбранных компонентов и применимые подписи. При совпадении входов артефакт сохраняет SHA производителя. Упаковщик берёт те же проверенные байты, которые передал сборочный job.

Доверенные записи кэша ограничены доверенными событиями основной ветки и проверенным workflow. PR использует разрешённое чтение. Ключи и пути на запись ограничены, секреты, ключи подписи, токены и данные пользователей исключены. Повреждённый или несовместимый результат заменить проверенной свежей сборкой либо остановить операцию. Подписание и публикация изолированы. Отслеживать объём записей и хранилища, ограничивать размеры, использовать автоматическое вытеснение и разграниченную очистку устаревших записей в пределах бесплатной квоты.

## 11. Доказательный выбор внутренних реализаций

Для существенного решения зафиксировать действующие требования, границы безопасности и измеряемый baseline. Сравнить текущий Aeris, релевантный функциональный эталон и подходящие альтернативы по исходникам, совместимости, лицензиям, надёжности, производительности и стоимости сопровождения. На этапе, предусмотренном [ROADMAP](ROADMAP.md), провести изолированное исследование при необходимости и получить независимое ревью. Сохранить результаты, риски, план миграции и откат в [DECISIONS](DECISIONS.md). Локальные исправления требуют проверок, соразмерных риску.

Допустимы проверенные Rust-компоненты, адаптация нескольких решений и идиоматическое портирование алгоритмов из других языков. Runtime, хранилище, очереди, буферы, схемы внутренних данных, MVVM-библиотеки и инструменты сборки пересматриваются при достаточных доказательствах. Публичные контракты IPC и API, границы привилегий и утверждённые форматы сохраняются. Нативность сетевых подсистем не разрешает Go runtime, сетевые движки Go/C/C++ через FFI или внешнее ядро. Исключения описаны в [SPECIFICATION](SPECIFICATION.md).
