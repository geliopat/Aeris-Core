# Configuration implementation status / Статус конфигурационного модуля

Development branch, not a stable YAML contract.

- The original UTF-8 text is kept privately, unchanged; no serialization back into a provider subscription.
- Single document, 16 MiB input cap, bounded parser budgets; reject duplicate keys, unsupported tags and includes. Diagnostics never print input text, parser excerpts or supplied values.
- Initial structural checks cover basic mode/ports/booleans, TUN and DNS field shapes, proxy/group identities, common references, and an iterative cycle check. Rules preserve provider ordering; user rules are a separate ordered sequence and a preview places them first.
- The checker accepts a provider-declared `GLOBAL` proxy group. Rules and `dialer-proxy` may target an implicit `GLOBAL`. Group members must reference a declared `GLOBAL`, which may appear later in the YAML. An explicit group participates in duplicate and cycle checks. Actual group construction and selection remain runtime work.
- Top-level `hosts` accepts an omitted, null, or empty mapping (CFG-01, DNS-02). Nonblank keys map to a nonblank string or a nonempty list of nonblank strings. FlClashX models scalar entries and its pinned core also accepts lists and singleton aliases, with special handling for `lan`. The synthetic fixture verifies that scoped IPv6, aliases, and other strings are preserved in the original YAML. Blank keys or values fail the structural check. Domain matching, alias cycles, literal-address validation for multi-value entries, and local resolution require separate checks before runtime activation. ## Immutable profile candidates

The internal ProfileStore publishes structurally checked immutable snapshots, with independent user rules and a generation precondition. Invalid candidates and stale writers leave the old snapshot unchanged. Existing readers retain the old snapshot; one previous snapshot can be restored with a new generation. This is in-memory candidate storage only; there is no active configuration, disk persistence, live socket migration or runtime rollback yet. User rules with supported simple matchers are checked against candidate proxy/group/provider references. Complex matcher semantics and nested fields remain unchecked. The CLI accepts both `config check` and the documented `config test` alias.

### Separate user-rule and provider updates (CFG-02, CFG-03)

User edits submit an ordered in-memory `UserRules` value through `ProfileStore::update_user_rules`. Each entry retains its text and enabled state. Enabled entries precede provider rules in their submitted order. Disabled entries stay available for editing and are excluded from effective order, structural rule checks, and unreachable-rule diagnostics. All typed entries count toward the 16 MiB per-rule, 32 MiB total text, and YAML event-derived count limits. The existing YAML sequence of strings still loads with every entry enabled under its original decoder limits. Provider YAML remains byte-for-byte unchanged by user edits.

`ProfileStore::refresh_provider` retains the current user entries and validates enabled entries against the candidate provider. If a refreshed profile removes a target referenced by an enabled rule, the refresh fails with the current and previous snapshots retained. A caller can edit or disable the affected rule and retry with the latest generation. Only one valid edit or refresh for the same generation can publish. The losing valid candidate reports a conflict, and an invalid candidate can report its validation error. Rollback restores the previous complete in-memory snapshot under a new generation. This change covers candidate handling. GUI and IPC wiring, on-disk storage and runtime activation remain open.
