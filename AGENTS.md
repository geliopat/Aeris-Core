# Aeris — обязательные инструкции разработчикам и ИИ-агентам

## 1. Источник требований

Перед началом задачи читать SPECIFICATION, ARCHITECTURE, ROADMAP, CONFIGURATION, PROVIDER-HEADERS, UI-SPECIFICATION, TESTING, COMPATIBILITY. Позднее явно утверждённое решение пользователя отменяет противоречащее раннее. Не расширять scope ради количества функций. Если контракт не утверждён, помечать TBD, не выдавать предположение за решение. Применять [D-26](docs/DECISIONS.md#d-26--выбор-реализаций). Внутренние решения выбирает оркестратор по доказательствам и независимому ревью. Изменение утверждённых границ или обязательного поведения требует разрешения владельца. Не считать этот комплект существующим кодом или проверенными результатами. Прочитать также [DECISIONS](docs/DECISIONS.md), [DEFAULTS](docs/DEFAULTS.md), [REQUIREMENTS](docs/REQUIREMENTS.md), [UPSTREAM](docs/UPSTREAM.md), [STATUS](docs/STATUS.md), [AGENT-RESPONSIBILITIES](docs/AGENT-RESPONSIBILITIES.md) и [RELEASES](docs/RELEASES.md). Прочитать также [UPSTREAM-LICENSES](docs/UPSTREAM-LICENSES.md) и [DEPENDENCY-POLICY](docs/DEPENDENCY-POLICY.md). При конфликте не применять более раннее отменённое решение. Статус проверять по актуальному HEAD/CI, не по дате старого отчёта.

Приоритет имеют последнее решение владельца, DECISIONS, действующие функциональные требования и архитектурные границы, профильные документы, DEFAULTS, ROADMAP, текущие реализации, исторические материалы и сторонние источники. Сохранить старые доказательства за точными ревизиями. Перед работой проверять текущие HEAD, CI, PR, локальные изменения и задачи агента.

## 2. Не нарушать

- Aeris — отдельный проект; не менять FlClashZ, его службы, файлы, ветки или automations.
- Windows 11 x64 / Windows 10 22H2 x64. Core Rust, GUI C#/WinUI3. Не подменять ядро внешним Mihomo/Xray/winws/winws2. Не добавлять Zapret1, самописную криптографию или C DPI FFI.
- Функциональный эталон Mihomo — точная сборка FlClashX. Источники реализации выбираются по D-26. MIPS обязателен для сравнения на этапе 9. XHTTP/XUDP/REALITY/Vision — оригинальный Xray. Для DPI действует приоритет Flowseal на Zapret2, оригинального Zapret2 и zapret2-gui. Для WireGuard/AmneziaWG действуют официальные эталоны из UPSTREAM. Углублённое исследование этих источников DPI и AmneziaWG начинать на этапах 10 и 6 соответственно. Соблюдать лицензии, фиксировать ссылки и commits. Не копировать чужой код без проверки права использования.
- VPN/DPI независимы, DNS имеет собственный lifecycle. Не модифицировать прокси-транспорт DPI по умолчанию. Не допускать скрытых утечек или обхода Kill Switch. Не выполнять произвольные BAT/CMD/Lua OS commands от SYSTEM.
- CLI `aeris` из любой директории pwsh, GUI `Aeris.exe`, ядро `aeris-core.exe`, сервис `AerisCore`. Не полагаться на регистр файлов Windows. Не создавать alias clash.
- YAML подписки неизменяем, пользовательские правила отдельно и приоритетнее. Не вводить общий override, `nooverride`, Lua config overrides. Отдельный адаптированный Mihomo template Remnawave.
- Только два режима UI: без providermode простой, с providermode полный. Нет ручного переключателя, редактирования виджетов, IP в простом; полный IP всегда при наличии, без анонса. Соблюдать согласованное размещение UI и общий hover glow. Не возвращать старые макеты, popup выбора или ранее отвергнутые функции.
- Release/Nightly, без Preview. Нет отдельного полного backup/export настроек. Внутренний rollback остаётся. Не публиковать стабильный Release до gate 1.0.0.
- Не вводить телеметрию, аккаунты, лишние зависимости, неподтверждённые параметры и скрытые fallback. Не логировать токены/приватные ключи/полные URL подписок без защиты.

- Сохранять слабую связанность GUI/ядра/служб и версионируемые внутренние контракты. Полноценная система модулей, Plugin Manager, публичный API/SDK и каталоги отложены до стабилизации. Конкретные модули требуют разрешения владельца. Не загружать произвольный сторонний код в привилегированные процессы.

## 3. Рабочий процесс

1. Проверить актуальную ветку, файлы, требования и upstream refs. Не путать эталон с целевым репозиторием.
2. Сделать соразмерный риску план, определить затронутые модули и тесты.
3. Изменить код, тесты, схемы/контракты и документацию совместно. Не оставлять дублирующий код, мёртвые ветви, необъяснённый unsafe и скрытые ошибки; актуальные стабильные версии инструментария и зависимостей использовать после проверки совместимости, фиксировать lockfiles, документировать public API и причины исключений. Не отключать предупреждения/проверки ради зелёного CI.
4. Запустить доступные проверки, сообщить команды, результаты, ошибки и недоступные среды. Не выдавать сборку за тестирование. Не отмечать непроведённый тест как PASS.
5. Проверить security, regressions, error paths, IPC compatibility, rollback и производительность по необходимости.
6. Подготовить проверяемый diff/PR, provenance, ограничения. Не сливать при fail обязательных тестах.
7. Создавать/изменять репозитории, запускать сборку, публиковать Release и менять инфраструктуру только в рамках полученного разрешения. Не запускать сборки в ответ на обсуждение дизайна или подтверждение пункта ТЗ.

CI/CD ведёт DevOps по [архитектуре](docs/ARCHITECTURE.md#10-cicd-и-переиспользование-компонентов) и режимам [FAST, FULL и CLEAN](docs/RELEASES.md). Использовать доступные бесплатные hosted runners. Сохранять обязательные проверки, границы доверия и подтверждать ускорение измерениями.

## 4. Качество и безопасность

Rustfmt/Clippy/Cargo Test/Audit/Deny, Roslyn/dotnet format, unit/integration/fuzz. Асинхронность, bounded queues, cancellation, typed errors. Минимальные права, IPC ACL, явные capabilities, подписанные манифесты с доверенными ключами, хэши, atomic replace, path validation, архивы без traversal. Никаких случайных privileged shell scripts. Lua sandbox/изоляция по threat model, проверка лицензий/подписей ресурсов. Секреты DPAPI/redaction; нет автоматической отправки логов.

## 5. Отчётность

Отдельно указывать: что реализовано, что проверено, что не проверено и почему, что осталось, какие предположения сделаны. Утверждения о производительности и совместимости — только на основе реальных измерений/версий. Никаких обещаний фоновой работы без созданного механизма автоматизации. В каждом релизе обновлять документацию RU/EN, changelog, матрицу совместимости и manifest.

## 6. Координация Codex

Главный оркестратор — единая точка интеграции и изменения общих контрактов. Ролевое распределение и порядок передачи результатов описаны в docs/AGENT-RESPONSIBILITIES.md. Привязывать изменения к ID из docs/REQUIREMENTS.md. Не считать перечень требований автоматически выполненным; отметить конкретные тесты, SHA, ограничения, PASS/PARTIAL/FAIL/SKIPPED. Общие API/YAML/IPC, схемы и файлы сборки меняет назначенный владелец, а не несколько агентов одновременно. Не перезаписывать работу другого агента и не сливать непроверенные ветки. Перед интеграцией сверять актуальные решения, defaults и исключения. Проверять, что зависимости, фикстуры, upstream и CI не возвращают отменённые требования. Не спрашивать владельца повторно по уже принятым решениям; существенный неразрешённый TBD вынести одним конкретным вопросом.
